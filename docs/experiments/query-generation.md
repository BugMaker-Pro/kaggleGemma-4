## 固定查询菜单探索性试跑（2026-11-02）

这是[后续研究计划](../archive/history.md#research-directions)第一阶段的实现与运行记录。它验证无金标检索、独立评分及固定菜单的选择空间，不是证据状态控制器，也不是确认性方法实验。

## 冻结的输入与范围

本轮目录：[query-pilot-20261102-v1](../../experiments/runs/query-pilot-20261102-v1/manifest.json)。Manifest 在检索及新结果评分前生成，记录源码与输入 SHA256；运行和评分都会校验。后续修改代码必须新建运行目录，不覆盖这轮产物。

- 来源：历史上已用于开发的 SWE-bench Lite 任务。
- 抽样：种子 20261102，按 SHA256(seed, instance_id) 在各仓库内排序，每仓库取一条，共 12 条；不使用补丁、金标或历史命中信息。
- prepare 阶段从原始任务文件写出仅含 instance_id、repo、base_commit、problem_statement 的独立输入。
- run 阶段严格拒绝额外字段，只读取清洗后任务及修复前源码。完整原始任务文件路径仅用于来源记录，不由 run 阶段打开。
- 独立 evaluate 阶段在轨迹保存后才读取 gold_symbols.jsonl；金标及命中情况不会回传查询策略。
- 采用精确规范化符号 ID；未进入索引的目标仍计入分母。该定义不采用历史部分脚本的备用名称映射，数字不直接与历史表相减。

## 菜单与共同排序

原始 issue 查询作为共同起点；四个补充动作分别抽取标识符/路径、代码块、去除代码块和栈帧后的描述、栈帧。保存对应 issue 字符区间，仅表示 issue 中出现过该文字，不表示已获得代码行为证据。没有可检索文本的动作标为不可用，不替换为其他查询。

所有动作检索同一份全仓库 BM25 索引：现有节点元数据加每节点最多前 80 行正文。排序使用确定性的词项遍历与符号 ID 并列规则。保留现有图构建器的节点范围，包括模块节点；模块文本与符号文本的重叠是本索引的限制。

固定策略选择“标识符/路径 + 描述”两个补充动作；不可用动作不执行。用 RRF（常数 60）统一融合、截断到 200 个候选，并直接取前十作为诊断排名。未接入最强学习融合模型，因此 recall@10 仅是本轮排序的诊断，不能作为新方法相对历史强基线的成绩。

## 预算及成本

| 项目 | 本轮上限或规则 |
| --- | --- |
| 部署动作 | 1 次原始查询 + 最多 2 次补充查询 |
| 每动作返回 / 最终候选 | 200 / 200 |
| 原始 issue / 每个补充查询 | 20,000 / 4,000 字符 |
| 每个部署组合累计查询文本 | 28,000 字符 |
| 每个部署组合评分文档次数 | 300,000，跨查询重复评分重复计数 |
| 模型调用与 token | 0；本轮不使用模型，不把字符数称为模型 token |
| 源码 / 索引节点 | 50,000,000 字符 / 100,000 节点；超限保留失败记录 |
| 缓存与重试 | 每任务新建索引，无重试 |
| 时间 | 实测并报告，没有硬超时，不声称等实际耗时 |

源码字符上限在读取后检查，不能当作读取过程的硬 IO 限制。源码读取、建图与索引是各动作共有的前置成本，单独记录。候选评分次数统计有匹配分数的文档数，不是内部词项访问次数。

完整菜单为离线诊断执行，可能超过任意部署组合的预算。保存整轮实际执行时间；各组合的搜索成本由对应动作的已测开销相加得到，是回放估计，不是独立运行这些策略的耗时。无效填充不计为公平性措施。

## Oracle 与判读

Oracle 只在预算可行的动作子集中选择，以候选目标覆盖为目标。融合与候选截断先按部署规则完成，再使用金标评分；不能让金标从候选并集中额外挑选保留目标。覆盖并列时先选较少动作，再按动作名打破并列，不用前十命中率打破并列。

主要比较：预算约束 oracle 减去固定组合的任务宏平均候选覆盖。其他覆盖和 recall@10 比较均为描述性诊断。全菜单并集单独报告，不作为可部署策略的得分。

继续投入的工程参考门槛预先设为 +0.02（2 个百分点），不是预期提升或显著性阈值。报告以仓库为单位的配对 bootstrap 描述性 95% 区间（2,000 次，种子 20261102）：

- 区间整体低于门槛：本菜单未显示值得继续投入的差距。
- 区间整体达到门槛：值得进一步开发，但不代表控制器已能取得该增益。
- 区间跨过门槛，或不足两个可评分仓库：不确定。

12 条历史任务只能提供初步诊断，bootstrap 不保证小样本下的可靠覆盖率。缺失金标与无 Python 符号任务单独报告；有金标但检索失败的任务按零覆盖计入，不能静默删除。不自动扩样，不根据本轮结果改门槛。

固定菜单的 oracle 不能限制读取代码后才生成的新查询。无论这份菜单是否成功，后续反馈生成探测均需单独的冻结配置。

## 运行结果

本轮 12 条任务全部完成且可评分，零失败；完整菜单执行约 90.49 秒、47 次检索调用，没有模型调用。源码字符量累计 84,430,315；这是各任务共有的预处理输入量，不能隐藏在查询成本之外。

| 策略 | 候选目标覆盖（宏平均） | Symbol recall@10（诊断） |
| --- | --- | --- |
| 原始查询 | 62.50% | 25.00% |
| 固定组合 | 58.33% | 33.33% |
| 预算约束的覆盖 oracle | 66.67% | 25.00% |

主要差值为 +8.33 个百分点；仓库 bootstrap 描述性 95% 区间为 [0.00, 25.00] 个百分点，跨过预定的 +2 点门槛，故冻结规则给出的结论是 **不确定**。不自动扩样，也不把 oracle 写成已实现方法的成绩。Oracle 优化覆盖，不能期待其 recall@10 同样最高。

逐任务核查发现：

- Oracle 相对固定组合的全部覆盖差距来自 pydata__xarray-5131：原始查询覆盖为 1.0，固定组合为 0.0，oracle 选择不补充而保留 1.0。这是避免退步的空间，不能解释为控制器已经补回更多遗漏。
- 相对原始查询，oracle 只在 pytest-dev__pytest-5413 增加 0.5 的任务覆盖，对总体贡献 +4.17 个百分点；固定组合在该任务也取得相同覆盖。
- 全菜单未截断并集覆盖为 83.33%，高于预算约束 oracle 的 66.67%。django__django-15996 与 mwaskom__seaborn-2848 的目标出现在动作返回并集中，但经过所有可行组合的共同 RRF 融合与 200 候选截断后都未保留。不能把并集数字当作部署收益。
- 原始查询、固定组合、oracle 对应的查询调用合计分别为 12、35、14；这是共同上限内的不同实际成本。47 次调用是生成整份诊断菜单的实际执行量，不是 oracle 的在线成本。

完成验证：12 项新增测试通过，仓库全部 115 项测试通过。覆盖了金标字段隔离、issue 引用位置、确定性排序、预算约束、先截断后 oracle 评分、未索引目标的分母、失败任务保留、快照端到端流程和配置篡改检测。

审计材料：[manifest](../../experiments/runs/query-pilot-20261102-v1/manifest.json)、[清洗后输入](../../experiments/runs/query-pilot-20261102-v1/tasks.jsonl)、[检索轨迹](../../experiments/runs/query-pilot-20261102-v1/trace.jsonl)、[逐任务评分](../../experiments/runs/query-pilot-20261102-v1/scores.jsonl)、[汇总](../../experiments/runs/query-pilot-20261102-v1/summary.json)。

## 候选保留对照与丢失诊断（2026-11-02）

结论：本次轮转保留规则没有改善固定查询组合的候选覆盖。12 条历史任务上，覆盖从 58.33% 降为 54.17%，没有任务改善，pytest-dev__pytest-5413 退步。候选丢失的位置可以确认，但“按查询均匀分配名额就能解决”没有得到支持。

本实验由[首轮固定菜单结果](query-generation.md#query-pilot)启发，复用相同 12 条任务，属于事后提出假设的探索性对照。新协议在新规则评分前保存；这不使已使用的任务变成未见测试，也不能据此确认新方法有效或无效。

## 问题定位

首轮的相同查询与预算不变。逐目标记录各动作返回排名、完整 RRF 融合排名、每条查询的分数贡献以及截断后的去留。

| 任务与目标 | 目标在查询中的位置 | RRF 融合后的变化 | 诊断 |
| --- | --- | --- | --- |
| xarray-5131：GroupBy.__repr__ | 原查询 115；代码查询 4 | 固定组合 277；原查询加代码查询 14 | 固定组合没选到已有的有用查询，同时挤掉原有命中 |
| django-15996：EnumSerializer.serialize | 标识符查询 130；原查询前 200 无目标 | 原查询加标识符 227；固定组合 289 | 单路较深的命中被融合截断 |
| seaborn-2848：HueMapping._lookup_single | 代码查询 190；原查询前 200 无目标 | 原查询加代码查询 251 | 固定组合未选代码查询；即使选到它，RRF 也未在预算内保留目标 |
| pytest-5413：ExceptionInfo | 标识符 163；描述 135 | 固定组合 161 | 多路较深的命中通过分数累加被保留，是轮转规则丢掉的命中 |

“前 200 无目标”只针对已保存动作返回，不表示整个索引不存在目标。xarray 的覆盖 oracle 选择“不补充”是少动作优先的并列规则；不能推断补充查询全无价值，代码查询也能保留该目标。

## 冻结的对照

一次只比较一种替代规则，不做参数搜索：

1. 原规则：对所选查询的候选并集计算 RRF（常数 60），取前 200。
2. 替代规则：原查询先行，补充查询按原 ACTIONS 顺序，轮流取一个尚未选入的候选；重复项跳过且不占名额，直到选满 200 或列表耗尽。
3. 替代规则选出的候选仍按同一完整并集的 RRF 分数及符号 ID 并列规则排序，因此只改变保留集合。

轮转规则不保证保留原查询的全部命中，也不保证保留每条补充查询的深层目标。每次动作仍最多返回 200，所选查询调用、文本和评分预算沿用父实验；对 oracle 只枚举同一份预算可行的动作组合。

主要比较是固定动作组合下，轮转保留减去 RRF 保留的宏平均候选覆盖。Oracle 与 recall@10 是次要描述性诊断。没有新增检索、模型或修复调用；0.0274 秒为所有动作组合的本地候选回放时间，不是部署选择器的完整运行成本。

新目录包含独立 manifest、无金标回放和独立评分结果。prepare 和 replay 不读取金标；evaluate 先重新计算并核验回放候选，再读取金标。父实验输入、源码和轨迹 hash 以及新实验源码 hash 均被验证，旧实验产物未修改。

## 结果

| 保留方式与动作策略 | 候选目标覆盖 | Symbol recall@10（RRF 诊断） |
| --- | --- | --- |
| RRF + 固定组合 | 58.33% | 33.33% |
| 轮转 + 固定组合 | 54.17% | 33.33% |
| RRF + 覆盖 oracle | 66.67% | 25.00% |
| 轮转 + 覆盖 oracle | 62.50% | 25.00% |

12 条全部可评分、零失败。主要差值 −4.17 个百分点；仓库 bootstrap 描述性 95% 区间为 [−12.50, 0.00] 点。区间包含零，且样本小、已用于开发，不作确认性显著性主张。

固定组合中，pytest 的两个金标目标原来保留一个，现在均未保留，该任务覆盖由 0.5 降为 0，导致总体下降 0.5 / 12。ExceptionInfo 在标识符、描述查询的贡献分别为 1/223 和 1/195，累加后 RRF 排名为 161。轮转提前用尽候选名额，没有走到该目标。另一个目标 ExceptionInfo.__str__ 不在任何已保存动作前 200 中，两种保留规则都无法救回。

Django 与 seaborn 的目标仍未保留，xarray 固定组合也仍未保留目标。轮转规则既没有解决单路深层目标问题，又失去了 RRF 对多路支持目标的保留优势。这个结果只适用于当前规则、菜单、样本与预算，不证明所有配额或融合策略都无效。

## Issue 查询生成在最强融合排序器上的增量验证（2026-11-03）

本轮复用[35 条任务扩样](feedback.md#flash-replication)已保存的只看 issue 生成的查询，不增加 API 请求。该批任务结果已经检查过，因此当前属于探索性诊断，不能重新称为未见测试。

问题：前一轮的查询生成收益在换用历史最强的“16 特征＋dense”排序器后是否仍然存在？查询生成只负责候选来源；所有候选的排序特征和 dense 查询均使用原始 issue，不把生成查询的 RRF 分数加到学习特征中。

## 冻结比较

| 名称 | 候选池 | 排序器 |
| --- | --- | --- |
| historical | 历史 metadata BM25 前 200 | 原仓库隔离两折、3 种子平均的 17 特征模型 |
| body_original | 前轮原始 issue 的正文 BM25 前 200 | 同一个冻结模型 |
| generated | 前轮原始正文查询＋两条 issue 生成查询，经 RRF 截断的前 200 | 同一个冻结模型 |

主要比较是 generated 减 body_original 的宏平均 symbol recall@10。generated 减 historical 为次要比较，避免把正文索引的变化算成查询生成贡献。候选数都不超过 200，但并集编码、模型评分和前轮查询成本不同，不能宣称等实际计算成本。输出 k=10，目标不在候选池仍计入金标分母。

本轮不包含反馈组、不改变查询、不训练新检索策略，不根据这 35 条的标签调模型参数。没有用参考补丁决定候选、特征、融合或停止。

## 排序器复现与折隔离

训练输入为原 data/features_full.jsonl 和 data/embed_retrieval.jsonl，全部 2,232 条。按排序后的仓库列表交替分组，两折训练任务数分别 692、1,540；每个评估仓库仅由另一组仓库训练出的模型评分。训练种子 0、1、2，300 轮，其余历史参数不变，仅显式限制两个 CPU 线程。

先复算全部任务的历史 symbol recall@10，与 data/dense_scores.jsonl 的 dense_symbol 逐任务比较。任何不一致均记录并停止，不通过在当前样本上挑参数来修正结果。模型文件保存并记录 hash。历史候选的 dense 值、BM25 标准化分数和排名保留原四舍五入及并列规则。

预测时再次验证历史候选的 17 列输入给出的分数与训练阶段保存的分数逐项相同。该复现能检查实现一致性，但不能排除历史数据开发使用或公共基准训练污染。

历史复现已完成：2,232 条逐任务 recall@10 与历史文件一致，均值 0.4470224841807413，零任务差异。六个模型固定后用于新增候选，两个仓库分组的评分与训练相互隔离。

实现修正记录：v1 在进入新候选评分前因缺少 validate_retrieval 导入而停止，原训练审计保留。v2 只补该导入，模型及方法参数没有变化，复用原六个模型并再次核验全部历史任务。新候选未使用 v1 的任何未完成输出，修正见[revision.json](../../experiments/runs/strong-query-20261103-v2/revision.json)。

## 新候选特征的明确扩展

历史模型只见过 metadata 前 200 的候选。新增候选分布不同，是本实验的固有限制，不能称为模型已在这种候选分布上验证。

- 全部词法、正文、路径和 dense 特征的查询仍是原 issue。
- graph near_seed 固定取历史 metadata 前五个种子。
- file_best、file_size 固定依据历史 metadata 候选池；新增文件若不在该池中，这两列为零。更换候选池不能悄悄改变原候选的上下文特征。
- 新候选 BM25 分数使用全仓库 metadata 文档统计和原 issue，按相同全局最大值归一化；排名取全库原 issue 的位置，并列按 ID，无匹配时用 N+1。
- 对原候选保留历史 BM25 两列，另外 14 列从修复前代码独立重建并逐项核验。原候选特征被改动即停止。

推理输入 anchors.jsonl 仅包含 ID、仓库、历史特征、路径和 dense 分数，不含 gold、labels 或补丁；训练标签只在独立训练阶段使用。

## 新候选 dense 分数

使用本机已有的 bge-small-en-v1.5，权重与 tokenizer 文件 hash 写入 manifest。原候选复用历史 dense 分数；新候选按历史方式编码：原 issue 前 1,200 字符加查询前缀，文档为路径、符号 ID 和前 800 字符源码，512 token 截断、fp16 CUDA、CLS 归一化、余弦四舍五入到四位。

模块节点沿用旧文档构造逻辑，正文匹配为空时只保留路径与 ID；不为新模型额外补全文本。新增候选使用新算分数、原候选使用已存分数，两者虽然配方相同，仍可能存在硬件和浮点差异；这不是独立验证历史 encoder 执行。

## 统计与继续投入规则

## 固定协议与成本边界

- metadata 和正文各取原始 issue 检索的前 200，等权 RRF，常数 60，排名从 1 开始。
- 两路分数按符号 ID 累加，按 RRF 分数降序、ID 升序去重排序，截断为 200 个候选。
- 只有候选集合改变；最终使用上一轮已保存的 17 特征模型分数。模型分数并列时沿用该候选池的原顺序，与父实验一致。
- 同一候选的强排序分数在所有方案中固定，不重新训练或编码，也不使用生成查询作为排序特征。
- 主要比较：generated 减 simple_fusion 的任务宏平均 symbol recall@10。按仓库做 5,000 次 bootstrap，种子 20261103；其他比较均为描述性诊断。不自动扩样。
- 先冻结 manifest，再完成不读取金标的候选回放，最后独立读取 gold 评分。目标不在候选池仍计入分母。

两个方案均保留 200 候选，但不声称等实际成本：简单融合需要两次逻辑检索、零次生成；生成方案需要三次逻辑检索及一次 Flash 查询生成。已有 35 条实验中的生成费用属于此前成本，本轮通过回放复用全部候选与强排序分数，新增 API 调用、dense 编码和模型推理均为零。

这是一项更便宜的基线，不是调用数完全匹配的基线；不能由它直接证明生成查询具有最优的单位成本收益。简单池平均去重并集为 337.57 个候选，只有其中 200 个进入最终强排序。

每条一次 Flash 请求，生成两条查询；关闭 thinking，temperature=0，JSON 输出，max_tokens=256。对照按等权 RRF（k=60）融合 metadata 与正文前 200 个候选，生成方案融合正文及两条生成查询，各保留 200 候选。使用既有按仓库隔离的两折、每折三个种子的强排序器和本地 bge-small；不重新训练、不调参。

主要指标为生成方案减简单融合的任务平均 symbol recall@10；按仓库 bootstrap 5,000 次，seed=20261103，预定值得继续的差值为 +2 个百分点。失败时生成臂完全回退至简单融合；不自动重试、不自动扩样。全部已选任务保留调用成本，无法评分的原因单列。

两条任务 django__django-10914、sympy__sympy-16106 缺少历史特征，按无金标原始逻辑重建 anchor，并重新本地编码；没有替换或删除。输入、源码、模型与请求均已冻结 hash，先完成候选评分再读金标。

这是与当前先导实验不重叠的历史 SWE-bench Lite 样本，仍不是全新未使用的确认性测试集。区间仅作描述性判断。

37/37 次生成请求成功，没有重试或回退；37/37 条本地评分完成。其中 35 条有可评分符号，另两条 django__django-10914、sympy__sympy-16106 的 gold 记录没有符号目标，单列为 no_symbols，不计入召回分母，但仍计入全部资源成本。
