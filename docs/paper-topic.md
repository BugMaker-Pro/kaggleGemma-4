## 1. 为什么换底座（v3 → v4）

v3 的主线是审计官方发布的 `graphs/`。三条理由让它必须换：

1. **数据被门禁挡住**：22.42 GB 只在主赛道 Data 页、需 Join + Accept Rules，论文赛道本身 writeup-only，没有数据。
2. **口径不可验**：官方图是黑盒产物，我们无法说明它的节点是怎么来的；审出来的缺口无法归因到「建图器」还是「打包」。
3. **Quality 维度要求跨出比赛可迁移**：审计一个榜单只能解释这一个榜单；而在公开基准上建立的测量协议，任何 repo-level agent 都能用。

**v4 保留 v3 的骨架**（覆盖率诊断 + 重建图 + 同预算检索对照），只把「官方图」换成「公开基准上的黄金符号」。官方 129 任务那一路降级为**可选加分项**：只要拿到数据，同一套代码直接跑，不用改协议。

## 3. 关键概念：三个不同的天花板

这篇论文的全部论证都压在把这三件事分开上。混在一起说就会写成「我们建了个图」：

| # | 天花板 | 定义 | 现在测到 |
| --- | --- | --- | --- |
| C1 | **黄金符号可得性** | 参考修复动过的符号，能在建出的图里找到的比例 | 100%（自检，见 §5 警告） |
| C2 | **候选池召回** | 这些符号有多少进了按名字检索的 top-60 | **46.2%** |
| C3 | **图扩散上限** | 这些符号有多少是 top-5 种子的一跳邻居 | **21.8%** |

**C2 < C3 的反面才是重点**：即使图扩散完美，也只能碰到 21.8%；而候选池本身就已经丢掉了一半以上的正确答案。所以「换个更花的图算法」在算术上不可能有作为——**要动的是候选生成**。

## 4. 方法与已交付的代码

流水线全部 stdlib、纯 CPU、单机可跑：

```powershell
$py = 'D:\pyenv\cpython-3.12.13-windows-x86_64-none\python.exe'
& $py experiments\gold.py --tasks data\swebench_lite.jsonl --out data\gold_symbols.jsonl --snapshots data\repos
& $py tools\run_experiment.py --jobs 6
& $py tools\analyse.py
```

| 模块 | 作用 |
| --- | --- |
| `experiments/patchfile.py` | 解析 unified diff，给出**变更行的锚点**（删行锚自己，增行锚 `old_line-1`） |
| `experiments/symbols.py` | `ast` 抽符号；行号 → 最内层符号 |
| `experiments/snapshot.py` | 不落盘读 tar 快照；`read_all_text` 单次解压（gzip 不能回退，逐文件读会变成 N 次全解压） |
| `experiments/gold.py` | E0：黄金符号 + **显式记录解析不了的锚点**（87 个），不静默丢弃 |
| `experiments/buildgraph.py` | 建图器，输出与官方 graph **同 schema**（`nodes[id,name,text]` / `edges[source,target,type,key]`） |
| `experiments/coverage.py` | 四分类精确/后缀/仅模块/缺失 |
| `experiments/retrieve.py` | BM25 + 一跳图扩散 + 字符预算计费 |
| `tools/analyse.py` | 配对差值、bootstrap CI、符号检验 |

**建图器的边分七种解析状态**，这是论文的第二个卖点——大多数工具把这些折叠成一个「边」：

`local` / `import` / `unique` / `suffix` / `external`（stdlib 或三方依赖，不是缺陷）/ `ambiguous` / `unresolved`

django 一个快照的实测（2,715 文件 / 38,651 节点 / 209,502 边 / 10.8 s）：

| 状态 | 边数 | 占比 |
| --- | ---: | ---: |
| unresolved | 71,436 | 34.1% |
| local | 40,257 | 19.2% |
| import | 32,648 | 15.6% |
| ambiguous | 31,514 | 15.0% |
| unique | 23,365 | 11.2% |
| external | 10,282 | 4.9% |

**只有 46% 的调用点能在仓库内解析到确定目标。** 这是一个可以独立引用的数字。

## 5. 已有结果（295/300 任务，2026-10-25）

**主结果：同预算配对对照（n=285）**

| 指标 | 纯文本 | 加图 | 差值 | 95% CI | 胜/负/平 | 符号检验 p |
| --- | ---: | ---: | ---: | --- | ---: | ---: |
| recall@1 | 0.093 | 0.098 | +0.005 | (−0.030, +0.039) | 15/14/256 | 1.000 |
| recall@5 | 0.207 | 0.225 | +0.018 | (−0.019, +0.056) | 21/16/248 | 0.511 |
| recall@10 | 0.269 | 0.298 | +0.029 | (−0.002, +0.059) | 17/7/261 | 0.064 |

两条臂看到的是**同一个候选池、同样的字符预算**，只有排序不同。差异在 r@10 上接近显著（p=0.064，17 胜 7 负），r@1/r@5 没有。

> ⚠️ **覆盖率 1.000 不是发现，是自检。** 黄金符号和建图器共用 `模块.符号` 这套 id 口径，本来就该全中。它证明分母分子对得上，**不能当论文结论**。真正的结论是 §3 的三个天花板。

**分仓库（r@10，文本 → 加图）**：django 0.292→0.319、sympy 0.174→0.239、matplotlib 0.283→0.312、scikit-learn 0.261→0.304、sphinx 0.281→0.219（**反向**）、pytest 0.250→0.188（**反向**）。

## 6. 已知设计缺陷与修法（必须先修再定稿）

**缺陷**：现在的 graph 臂只在 BM25 top-60 池内**重排**，永远拉不进一个池外邻居。一个名字跟 issue 不沾边、但确实是某种子被调用者的黄金符号，图本来能救——现在救不了。**这系统性低估了图的价值，也压低了 r@10 的差值。**

**修法**（代码改动小）：

1. graph 臂改为 **open arm**：top-5 种子的一跳邻居可以从**全图**补进来填满 10 个槽位，不限于池内；
2. 两条臂仍然各 10 个符号，字符预算对齐（`context_chars` 已在计费），保证不是靠塞更多上下文赢；
3. 加一条 **oracle 上界**：把池外邻居全部放开，报告图能拿到的绝对上限。

修完可能出现两种结果，两种都能写：

- **差值为正且显著** → 主线成立：「候选生成是瓶颈，图的作用是补召回而不是改排序」。
- **仍然不显著** → 更硬的负结果：「在这个规模上，代码图对定位无可测收益」，同时 §3 的三个天花板解释为什么。评审喜欢能省下别人时间的负结果。
