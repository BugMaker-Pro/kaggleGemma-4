## 1. 为什么是这个题（三条硬证据，不是拍脑袋）

**证据一：Quality 这一维明确问「跨出比赛还能不能用」。**
> "How general and universal is the Submission approach beyond the competition? Does your submission translate to other similar problems?"

纯审计一个榜单在这条上只能拿 2 分。而「覆盖率怎么量、图怎么补」是任何 repo-level agent 基准都需要的，天然可迁移。

**证据二：三个奖里两个不是「最佳论文」。**
Best New Resource 的原文举例是「新数据集 / 新工具 / 新软件」。这意味着**不必写出最好的论文，造出最有用的东西也能拿 $10k**。本方案同时够 Best Paper 和 Best New Resource 两条线。

**证据三：评委和题目清单都在图这一侧。**
评委 Elan Markowitz（Google）；引用名单含 Bryan Perozzi（node2vec）、Michael Galkin、Benedek Rózemberczki。四个推荐题目里三个围绕 code graph，官方还专门发布了 `graphs/` 与 `embeddings/` 两个资产。

**结论**：把「图」放在标题里，比把「评测效度」放在标题里，期望分高一个档。

## 2. 题目与主张

**候选标题**

1. *What the Graph Misses: Measuring and Repairing Code-Graph Coverage for Repository-Level Agents*
2. *Coverage Before Cleverness: How Much Code Graph Is Actually in Your Code Graph?*
3. *A Coverage-First Benchmark for Code Graphs in Agentic Software Engineering*

选 1。

**核心主张（三句话，Abstract 就照这个写）**

> 官方为 129 个公开任务发布的代码图与符号嵌入存在系统性缺口（129 个 0 字节文件、async 符号缺失）。
> 我们在 129 个任务上给出黄金符号覆盖率，并按缺口来源分解；再用同一批源快照重建一张图，把覆盖率从 X% 提到 Y%。
> 结果显示：**图引导定位的收益几乎全部来自覆盖率提升，而不是图算法的复杂度**；在同等 token 预算下，重建图 + 简单扩展检索优于纯文本检索。

**为什么这句话重要**：它把「做更花的图算法」这个默认方向挡掉了，给出一个可操作的工程判据。评审读起来是一个结论，不是一个 bug 报告。

## 3. 研究问题与假设

| ID | 问题 | 需要的数字 |
| --- | --- | --- |
| RQ1 | 官方图/嵌入对「黄金修复符号」的覆盖率是多少？ | 覆盖率 k/N，按仓库与符号类型分解 |
| RQ2 | 缺口从哪来？文件级缺失、符号解析失败、还是引用没解析？ | 三类占比 |
| RQ3 | 重建之后，图引导检索比纯文本检索强多少？代价多少？ | recall@1/5/10 + token 成本 |
| RQ4（可选） | 这个增益会传导到 resolved 率吗？ | 小样本 A/B，没算力就删 |

| ID | 假设 | 证伪条件 | 证伪了怎么写 |
| --- | --- | --- | --- |
| H1 | 官方覆盖率 < 50% | > 80% → 图是好的，缺口在别处 | 转写「图可用但没人用」：分析官方工具的使用成本 |
| H2 | 缺口主因是文件级缺失（0 字节），占比 > 60% | 主因是符号/引用解析 → 更难但更值钱 | 结论改为「建图器比图数据更缺」 |
| H3 | 重建后 recall@5 提升 ≥ 10 个点，且 token 不劣于文本检索 | 无显著差异 | **负结果**：「图不是定位瓶颈」——对有 129 任务证据的论文同样成立，且省下读者的时间 |

三条全证伪也是一个干净的结论。**没有失败模式，只有不同结论**——这是这个题最值钱的性质。

## 4. 方法：五个实验

### 4.0 官方资产格式（2026-10-20 从主赛道 Data 页核实）

> 论文赛道本身没有数据（writeup-only）。数据在主赛道 `gemma-4-developer-agent` 的 Data 页：**22.42 GB / 524 files**，需 Join + Accept Rules 才能看到。

| 资产 | 格式 | 关键字段 |
| --- | --- | --- |
| `tasks.jsonl` | 行 JSON，129 条 | `instance_id` / `repo` / `base_commit` / `problem_statement` / `patch` / `test_patch` |
| `snapshots/` | 129 个 tgz | 冻结在 `base_commit`，未来提交已删除 |
| `graphs/` | NetworkX JSON，256 文件（129 任务名 + 127 commit 名，硬链接） | `nodes[*].id`（全限定符号）/ `name` / **`text`（符号完整源码）**；`edges[*].source/target/type/key` |
| `embeddings/` | `.npz`，256 文件 | `<node_id>.npy`，float32 × 256 |
| `wheels/` | 124 个 whl | 离线依赖，`/wheels/` 只读挂载 |
| `docker/`、`sandbox/` | 容器规格 + 初始化脚本 | 构建 `swebench-sandbox` |

三条对实验的硬含义：

1. **节点自带 `text`** → 覆盖率可在符号级严格计算，无需先重建即可比对。
2. **129 任务 ↔ 127 commit** → 硬链接去重必须做，否则覆盖率重复计数。社区报告的「129 个 0 字节」最可能就是打包时硬链接断掉，**待数据落地核实**。
3. **官方策展期已跑 fail-to-pass / pass-to-pass** → 「参考修复过不了验证」这条上界风险被官方堵死，v2 的正负对照审计因此不再是主线（已降级）。

### E0 黄金符号抽取（1 天，纯 CPU）

输入 `tasks.jsonl` → 取 `patch` → 解析出：变更文件、变更行号、所在符号（函数/类/方法）、新增/删除的行数。

产出 `data/gold_symbols.jsonl`，一行一个任务。**人工抽检 20 个**，报告标注一致率。

> 这是全篇的分母。分母错了，后面全错。所以先做、先抽检、先公开。

### E1 官方图审计（1 天）

对每个任务检查 `graphs/<id>.*` 与 `embeddings/<id>.*`：文件是否为 0 字节、能否解析、是否含符号、是否含 async 定义。

产出：**覆盖率矩阵**（任务 × 工具 × 是否覆盖黄金符号），以及缺口归因（文件级 / 符号级 / 引用级）。

### E2 重建图（3–4 天，纯 CPU）

用 `tree-sitter`（多语言）或 Python `ast`（先只做 Python 仓库）抽取：

- 定义节点：module / class / function / method，带签名与 docstring 摘要；
- 引用边：调用、import、继承；
- 解析策略：同文件 → 同包 → 全仓库唯一名匹配；解析不了的边单独标记为 `unresolved`（这个比例本身就是 H2 的证据）。

产出：`graph/<任务>.json`（节点 + 边 + 解析状态），以及一个**通用建图器**（对任意 repo 可跑）——这是 Best New Resource 的实体。

### E3 检索对照（3–4 天）

固定 issue 文本，比较三种定位器在 `recall@k` 上的表现：

| 条件 | 检索器 | 图 |
| --- | --- | --- |
| T0 | BM25 over 文件/符号名 + docstring | 无 |
| T1 | BM25 + 一跳图扩展（调用者/被调用者） | 官方图（可用的部分） |
| T2 | BM25 + 一跳图扩展 | 重建图 |

同时记录每次检索塞进上下文的字符数——**同预算比较**，否则图赢了也是因为塞得多。

产出：recall@k 曲线（三条线）+ token 成本表。**这是论文的主图。**

### E4（可选）传导实验（2 天，需 GPU）

把 T0 / T2 的候选集塞给一个小模型做定位选择，看是否改变化 resolved 率。算力不足就删，写进 Future Work。

## 5. 指标与主图

| 指标 | 定义 |
| --- | --- |
| 覆盖率 | 黄金符号能在图中找到的比例（分子/分母都要给） |
| 缺口归因 | 文件级 / 符号级 / 引用级 三类计数 |
| recall@k | k ∈ {1,5,10}，按任务平均 |
| token 成本 | 检索结果进上下文的字符数 |
| 解析成功率 | 重建图时边被解析（非 unresolved）的比例 |

**主图**：左panel 覆盖率条形图（按仓库，官方 vs 重建），右 panel recall@k 三条曲线。一张图讲完。

**第二张**：缺口归因的堆叠柱（三类来源），支撑 H2。

## 8. 风险

| 风险 | 概率 | 应对 |
| --- | --- | --- |
| `embeddings` 全是 0 字节 → 无法评估官方嵌入质量 | 高 | 明确声明不评嵌入，只评图；自建嵌入放 Future Work |
| 重建图效果不如 BM25 | 中 | H3 证伪，写成「图不是瓶颈」的负结果，仍是资源交付 |
| 黄金符号抽取歧义（patch 行 → 符号映射） | 中 | 人工抽检 20 个，报一致率；歧义样本单独列出 |
| 建图器跨语言难 | 低 | 四个仓库全是 Python，先只做 Python，多语言写 Future Work |
| 被判「没新意」 | 中 | 主图是「覆盖率 vs 收益」的因果链，不是「我们建了个图」 |
