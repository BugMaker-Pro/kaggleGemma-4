# 规模复核：2,294 个任务上的三个头条结论

一句话：**刻度差距原样复现；「图没用」只在文件层成立；「证据覆盖值 +8.6」不复现。**

## 数据规模

| 项 | 值 |
| --- | --- |
| 完整 SWE-bench test split | 2,294 个实例 |
| 可评分（黄金符号能解进图） | **2,232**（97.3%，62 个无解） |
| 唯一仓库快照 | 2,174 个，18.45 GB |
| 仓库数 | 12（与 Lite 完全相同） |
| 特征行 / 候选 / 正例 | 446k 候选，2,870 个黄金符号 |
| 特征构建耗时 | 10,797 s ≈ 3.0 h（6 进程） |

Lite 的 300 个实例全部包含在内；两份文件用同一套 `tools/features.py`、同一套指标口径（分母是任务的全部黄金符号，池外的算漏）。

## 三项对照

| 结论 | Lite（290） | 完整（2,232） | 是否复现 |
| --- | --- | --- | --- |
| 文件 vs 符号的刻度 | 0.624 / 0.275 = **2.27×** | 0.564 / 0.248 = **2.28×** | ✅ 几乎一模一样 |
| 图臂 vs BM25（符号） | +0.012，CI 含 0，p=0.50 | **+0.022，CI (0.013, 0.031)，p<0.001** | ⚠️ 变大且显著了 |
| 图臂 vs BM25（文件） | −0.010，p=0.50 | **+0.000，CI (−0.009, 0.008)，p=0.36** | ✅ 仍是零 |
| 学习排序 vs BM25（符号） | +0.057，p=0.016 | **+0.113，CI (0.098, 0.128)，488W/123L** | ✅ 变强 |
| 学习排序 vs BM25（文件） | — | 0.564 → **0.643**（+0.079） | 新增 |
| **排序 + 证据覆盖 vs 排序** | **+0.029，p=0.035** | **−0.002，CI (−0.008, 0.004)，p=0.41** | ❌ **不复现** |
| 排序里去掉图特征 | −0.017，p=0.50 | **+0.027，CI (0.017, 0.036)，p<0.001** | ⚠️ 反过来显著了 |

后两行是这次跑出来最重要的两个意外。

## 意外一：证据覆盖被排序器「吸收」了

同一段代码、同一个 cap、同一个阈值，只是训练任务从 ~145/折 变成 ~1,100/折：

| 臂 | r@10 |
| --- | --- |
| BM25 | 0.248 |
| 学习排序（16 特征） | **0.361** |
| + 证据覆盖 cap=1 | 0.362（vs 排序 +0.001，p=1.0） |
| + 证据覆盖 cap=2 | 0.362（+0.001，p=1.0） |
| + 证据覆盖 cap=5 | 0.359（**−0.002**，p=0.41） |
| + 证据覆盖 cap=10 | 0.335（−0.025，p<0.001） |

Lite 上「排序 0.332 → +证据 0.361」的那 2.9 分，在全量上**一点都拿不回来**，cap 越大越差。

解释（可信、且与数据一致）：`body_line`、`body_run`、`frame_hit`、`named_file` 本来就是 16 个特征里的四个。训练任务只有 145 个时，树模型学不动这几个稀疏特征，于是手写的「把证据候选提到最前五」补上了这个缺口；训练任务到 1,100 个时，模型自己学会了，手写规则只剩「挪走 5 个更好的候选」的副作用。

**所以那 2.9 分的功劳属于数据量，不属于规则。** 这也意味着 Lite 上 0.361 这个数是被小样本抬高的。

## 意外二：图的 2 分是真的，但只在符号层

2,232 个任务上，`graph_rerank` 相对 BM25 是 **+2.2 分**，CI (1.3, 3.1)，169 胜 90 负，12 个仓库里 8 个为正——**显著**。290 个任务时它是 +1.2、CI 含 0，所以我们当时写的是「检测不到」；样本量上去以后就检测到了。

但同一臂在**文件层是 +0.000**，CI (−0.009, 0.008)，81 胜 94 负，5/12 仓库为正——干净利落的零。这恰好是论文真正的论点：**图的收益在「哪个符号」上有一点点，在「哪个文件」上一点都没有**，而文件的差别正是 0.564 与 0.248 的那 2.28 倍所在。

排序器内部也一样：去掉四个图特征从 0.361 掉到 0.334（−2.7 分，p<0.001）。图特征在**有足够数据**时是有用的，只是有用的量级是 2–3 分，不是 10 分。

## 按 issue 信号拆分（粗略代理，不可与 Lite 的比例对比）

| 子集 | n | 占比 | BM25 | 排序 | Δ |
| --- | ---: | ---: | ---: | ---: | ---: |
| 候选正文里有行被 issue 引用 | 1,071 | 48.0% | 0.278 | **0.428** | **+0.150** |
| 只出现路径 / 帧 | 151 | 6.8% | 0.295 | 0.544 | +0.249 |
| 两者都没有 | 1,010 | 45.3% | 0.209 | 0.262 | +0.053 |

注意：这里的「quotes code」用的是 `features.py` 的 `body_line`（候选正文任意一行 ≥15 字符出现在 issue 里），比 Lite 的 `line_quote`（黄金正文被 issue 原文引用）**宽松得多**，所以 48% 与 Lite 的 23% 不是同一件事。要看严格的拆分，需要在全量上再跑一遍 `body_evidence.py`（约 2 小时）。

即便如此，方向仍然一致：**收益集中在 issue 写出源码的那些任务**（+15.0 分），没有信号的那 45% 只拿到 +5.3 分。

## 复现命令

```powershell
$py = 'D:\pyenv\cpython-3.12.13-windows-x86_64-none\python.exe'
& $py tools/fetch_repos.py --jobs 8 --index data/swebench_full.jsonl      # 2,174 个快照
& $py tools/features.py --tasks data/swebench_full.jsonl `
       --out data/features_full.jsonl --jobs 6 --append                    # 3 h

$venv = '.venv\Scripts\python.exe'
& $venv tools/run_combo_ltr.py --rows data/features_full.jsonl `
       --out data/combo_ltr_full.jsonl --orders-out data/combo_ltr_orders_full.jsonl
& $venv tools/run_combo_ltr.py --rows data/features_full.jsonl `
       --out data/combo_ltr_full_caps.jsonl --orders-out data/combo_ltr_orders_full_caps.jsonl `
       --caps 1,2,5,10 --skip-ablation
& $venv tools/analyse_full.py
& $venv tools/sensitivity_full.py
```

## 这次跑暴露的两个工具坑

1. `features.py` 原来跑完就写新文件，2,294 个任务要 3 小时，中途一断就全丢。加了 `--append`：读已有输出、跳过已完成的、追加写。实际用上了——第一遍跑的时候还有 1,000 个快照没下完，缺快照记为 `pending` 而不是 `failed`。
2. `run_combo_ltr.py` 原来把输出写死在 `data/combo_ltr.jsonl`，在完整集上跑会**覆盖 Lite 的结果文件**（论文里所有 0.361 都来自它）。加了 `--out` / `--orders-out`。
